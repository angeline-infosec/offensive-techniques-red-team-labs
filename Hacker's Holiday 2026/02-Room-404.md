## Scenario

He booked the quiet room. It's not on the floor plan, not in the brochure, not on any door. But port 8080 is wide open, and the rooms it never lists are the ones worth finding.

The Byte Lotus guest-experience platform went live in a hurry, and the night-shift developer shipped more than the website. The goal was to dump the exposed source code and find the flag.


## First contact

I navigated to `http://10.49.180.103:8080` and got the Byte Lotus homepage - a landing page for the hotel with a "Reserve a stay" button. Clicking it led to `/booking`, which just returned a 404 Not Found page. Nothing broken or suspicious on the surface, so the next move was directory enumeration to see what else was actually hosted alongside the homepage.

## Directory enumeration

I tried gobuster, and that gave a hidden directory named `.git/HEAD`.

`.git/HEAD` came back 200 which doesn't sound like much on its own, it's one small file. But it only exists inside a git repository, so if the server is handing it out, that means the entire .git folder is sitting in the webroot. And .git isn't just a leftover file, it's the project's full version control history: every commit, every past version of every file, potentially including things that were later removed but never actually deleted from history.

## Dumping the repo

Since manual path-guessing wasn't going anywhere, I used `git-dumper`, which doesn't rely on guessing - it walks `HEAD`, tries refs, and falls back to parsing whatever object structure it can reach:

```
 git-dumper http://10.49.180.103:8080/.git/ ./byte-lotus-git
```

Interesting detail: `.git/refs/heads/main` shows up as a successful `[200]` fetch inside the git-dumper log, on the same URL that 404'd when I curled it manually a few minutes earlier. Worth flagging honestly here rather than claiming git-dumper used some special fallback trick, since the log doesn't actually show one - it just fetched the same-looking path and got a different result.

## Why this worked

This one is a lot simpler than the prompt injection room - it's a straight deployment mistake rather than a logic flaw.

* The `.git` directory from the developer's local repo was deployed straight into the live webroot instead of being excluded. Anything under `.git/` was directly reachable and downloadable over HTTP, the same as any other static file.
* Directory listing was enabled on the web server, so browsing `/.git/` directly showed the full folder structure instead of returning a 403 (forbidden) or a blank response - that made it obvious there was something to dump.
* The README itself says it - this was meant to be an internal staging repo, and the flag comment literally says "remove before launch." The vulnerability isn't clever; it's a staging artifact that never got cleaned up before deploy.

## How I'd fix it

* Never deploy `.git` to a public webroot. Deployment pipelines should build/copy only the artifacts the app needs to run, not the whole working directory including version control metadata.
* Disable directory listing on the web server regardless. Even without `.git` exposed, an open directory listing on any path is handing out a map of the server for free.
* Add `.git`, staging configs, and README files with internal notes to `.dockerignore` / deployment exclude lists, not just `.gitignore` - `.gitignore` only stops git from tracking new changes, it does nothing to stop the existing `.git` folder from being copied wholesale during deployment.
* Never put secrets, flags, or "remove before launch" notes in a README or any committed file, even for staging. If it's sensitive, it shouldn't be typed into a file that gets committed at all.

## What I learned

This room was a good contrast to the prompt injection one - here the vulnerability is entirely mechanical. There's no trust logic to reason about, no framing tricks; it's just "was version control metadata left in a public-facing directory, yes or no." That makes it a good reminder that not every finding needs a clever angle - `gobuster` with a common wordlist and paying attention to what a 200 status actually implies (not just "page exists" but "this specific file structure exists") was the whole exercise.

The other thing worth sitting with is the `refs/heads/main` discrepancy. I didn't chase it down in the moment, and I should have - re-running the manual curl with `-v` right after the dump, while everything was still fresh, would have told me whether it was a request formatting issue on my end or something environmental. Noting it here honestly, instead of hand-waving it, is the right call, but the better habit going forward is to resolve loose ends like that before moving on, not after.

## Q&A

Q: What is an exposed `.git` directory, and why is it a security issue? 

A: It happens when a web server serves the `.git` folder - the local version control database for a project - as if it were regular static content. Since `.git` contains the full commit history, every version of every file, and often configuration or notes never meant to be public, an attacker who can browse or download it effectively gets the entire source code and history of the application, not just what's rendered on the live site.

Q: How do you test for this? 

A: Directory/file enumeration against common git paths - `.git/HEAD`, `.git/config`, `.git/index` - is the standard first check. A 200 response on any of those, especially `.git/HEAD` with valid-looking ref content, is a strong signal the whole directory is present and worth pulling.

Q: How do you actually extract the contents once you find it? 

A: Manually reconstructing a git repo from raw HTTP-served objects is possible but tedious - you'd need to parse `HEAD`, resolve refs, fetch zlib-compressed objects by hash, and decompress them by hand. In practice, a purpose-built tool like `git-dumper` automates this: it finds the ref, walks the commit → tree → blob object graph, downloads every reachable object, and runs a `git checkout` locally so you end up with a normal, browsable repo.

Q: How would you fix this one specifically? 

A: Exclude `.git` from whatever gets deployed to the webroot in the first place, disable directory listing on the web server as a general hardening step, and never commit secrets or "remove before launch" notes to files that end up in version control at all, staging or otherwise.
